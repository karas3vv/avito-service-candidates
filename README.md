# Кандидатогенерация объявлений услуг Авито

Текущая версия объединяет TF-IDF и BM25, после чего LightGBM выбирает 50 кандидатов. В репозитории находятся код, готовый `answer.csv`, модель и результаты локальной проверки. Все вычисления выполняются локально, без внешних API и предобученных моделей.

## Результаты

| Метод | Отложенные запросы: Recall@50 | Скрытый бенчмарк |
| --- | ---: | ---: |
| Исходная версия TF-IDF | 0,55375 | 0,519858 |
| BM25 с географическим сигналом | 0,72708 | не отправлялся |
| TF-IDF + BM25 + LightGBM | **0,92375** | пока неизвестен |

Все локальные строки таблицы рассчитаны на одних 400 запросах. Разметка включает все известные выборы для выбранного контекста запроса. По одному исходному выбору на запрос оценки составляют соответственно 0,555 / 0,7275 / 0,9225. Локальная оценка не гарантирует такого же результата на платформе.

## Воспроизведение

Проверено с Python 3.10. Скачайте [исходный архив задания](https://disk.yandex.ru/d/sNhfo0YOjGtufg) и распакуйте три Parquet-файла в `data/`.

```bash
git clone https://github.com/karas3vv/avito-service-candidates.git
cd avito-service-candidates
mkdir -p data
unzip /path/to/dataset.zip -d data/
python -m pip install -r requirements.txt
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=4 python src/solution.py
python scripts/validate_answer.py
sha256sum -c answer.sha256
```

Первый запуск строит индексы и признаки, обучает модель и записывает `answer.csv`, `model.txt`, `metrics.json`. Кэш `.cache_v2/` ускоряет дальнейшие эксперименты. Для повторного обучения на уже построенных признаках: `python src/solution.py --stage train`. Для полного запуска с чистым кэшем можно задать новый каталог через `--cache-dir`.

SHA-256 текущего CSV: `eb60c581d2bbe3fc67912ecaa8c3ef282e73d58b275cf000d2b46d82e78dc553`. Проверены формат файла, совпадение всех предсказаний при загрузке сохранённой модели и побайтовое совпадение CSV после повторного обучения на закэшированных признаках. Требуются память для разреженных индексов и около 1,2 ГБ для кэша, помимо исходных данных.

## Данные и признаки

`train.parquet` содержит положительные пары. `benchmark_items.parquet` задаёт весь доступный корпус, `benchmark_queries.parquet` — запросы для отправки. `query_id` используется только для записи CSV, `item_id` — для связывания записей и возврата ответа.

- Текст запроса сравнивается с заголовком, описанием и параметрами объявления. TF-IDF по словам и символам дополняется BM25 со стеммингом русского языка. Это позволяет учитывать словоформы и упоминания услуги вне заголовка.
- Текст фильтров запроса сравнивается с параметрами объявления, чтобы учитывать уточнения услуги.
- Поисковая локация, локация объявления и расстояние между координатами объявления и медианным центром локации помогают различать услуги в разных городах. Дополнительно используются частоты переходов между локациями из train.
- Подкатегория объявления оценивается по распределению подкатегорий для точного и похожих исторических запросов.
- Рейтинг, число отзывов, логарифм цены, длина заголовка и флаги доступности связи помогают модели выбирать среди текстово похожих объявлений.

Прямые частоты кликов по паре и популярность конкретного `item_id` исключены из признаков LightGBM: схема удаления отложенных пар могла бы создавать в них искусственный сигнал. Они не нужны модели для работы с новыми объявлениями. Категория поиска и флаг доставки используются в определении контекста разметки, но не как признаки итогового балла.

## Алгоритм

1. Строятся четыре TF-IDF индекса: слова и биграммы заголовка с параметрами, символьные n-граммы заголовка, слова описания, слова параметров. Дополнительно строятся BM25 индексы заголовка, первых 3 000 символов описания и параметров со стеммингом Snowball.
2. Объединяются кандидаты исходного метода, BM25, символьного поиска и поиска внутри локации. В среднем получается около 500 кандидатов на запрос; в набор гарантированно входят 50 лучших объявлений исходного метода.
3. LightGBM LambdaRank оценивает 32 текстовых, географических и числовых признака пары. Для отправки выбираются 50 объявлений с наибольшим баллом.

Размер модели выбран по отдельным 400 запросам: проверялись 50, 100, 150, 200, 250 и 300 деревьев. Выбраны 250. Параметры и seed находятся в коде. Использованы открытые библиотеки NumPy, pandas, PyArrow, SciPy, scikit-learn, LightGBM и snowballstemmer; версии закреплены в `requirements.txt`.

## Проверка качества и защита от утечек

Из train выбраны 2 400 фраз для обучения модели, 400 для выбора числа деревьев и 400 для проверки. В каждом срезе представлены редкие и частые фразы. После нормализации регистра и пробелов из обучения исключены ещё две пересекающиеся фразы: фактически модель обучается на **2 398 запросах**. Тексты обучающих запросов не пересекаются с текстами двух отложенных частей.

Для каждого выбранного контекста разметка включает все известные выбранные объявления в корпусе. Из статистик кликов удалены все повторения размеченных пар «нормализованный текст запроса — объявление», в том числе в других контекстах. Проверочные запросы не используются для обучения и выбора числа деревьев. Индексы строятся по доступному корпусу объявлений.

Дополнительная проверка на 350 запросах, чьи релевантные объявления не встречались среди обучающих ответов LightGBM, дала **Recall@50 = 0,92286**. Подробные результаты сохранены в `metrics.json`. Выборка всё равно ограничена объявлениями, встречавшимися в train и в корпусе бенчмарка; её распределение может отличаться от скрытых запросов.

## Анализ ошибок и изменения

В исходной версии хуже находились объявления без полного текста запроса в заголовке. В новой версии добавлены BM25, стемминг и более длинный фрагмент описания. Сочетание BM25 с географией подняло локальный Recall@50 с 0,554 до 0,727; отдельного измерения вклада только стемминга не проводилось.

Ручные веса исходного метода плохо сочетали текстовую близость, фильтры и географию. Обучаемый выбор из расширенного набора поднял метрику до 0,924. При проверке кода также обнаружено, что прежняя попытка добавлять локальные объявления не влияла на итоговую сортировку по тому же баллу. Теперь локальный поиск добавляет кандидатов, которые оцениваются отдельной моделью.

Остались два источника промахов: полнота расширенного набора равна 0,96625, поэтому часть релевантных объявлений отсутствует ещё до LightGBM; ещё 0,0425 среднего Recall теряется при сокращении набора до 50. Улучшение семантического поиска и отбора требует следующих экспериментов. Бенчмарк не использовался как источник разметки для подбора параметров.
